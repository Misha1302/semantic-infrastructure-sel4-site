Verification

A verified kernel is a foundation, not a proof of the whole system.

seL4 is attractive because its capability model and machine-checked proof story create an unusually explicit lower authority substrate. The project's semantic and temporal properties still need their own refinement and evidence.

Why seL4 fits the research question

The semantic layer speaks in domain concepts: objects, methods, ownership, temperature, deployment, emergency stop. seL4 exposes low-level kernel mechanisms: capabilities, endpoints, threads, address spaces, memory objects, notifications, and IPC. The project studies the refinement chain between those models: semantic contracts → candidate plan → verification/admission → privileged installation → kernel-enforced topology.

The non-negotiable boundary

Verified properties of seL4 ≠ verified Semantic Infrastructure OS.

Kernel verification does not automatically verify the Object Supervisor, candidate planner, plan verifier/admission logic, privileged installer, Invocation runtime, Streaming plane, residual guards, browser/interaction edge, device code, drivers, or deployment configuration. Nor does using seL4 by itself establish an end-to-end hard real-time guarantee.

What current seL4 material supports

Official seL4 material describes machine-checked proofs for properties such as functional correctness, with proof coverage depending on architecture/configuration. It also states explicit assumptions around hardware, boot/assembly and other low-level boundaries. The current release index lists seL4 16.0.0 and Microkit 2.3.1 as the latest versioned releases as of 2026-09-20.

Microkit is designed for statically structured systems, which makes it attractive for a first bounded topology experiment but not automatically the final answer for dynamic lifecycle requirements.

Project verification research track

A plausible assurance path can connect semantic policy to concrete topology rather than jumping directly from “kernel verified” to “system verified”:

Semantic authority / consistency / temporal contracts
  ↓ compilation
Candidate SystemPlan
  ↓ verification / admission
VerifiedPlan
  ↓ privileged installation
Installed capability/resource/scheduling topology
  ↓ implementation relation
User-space runtime + seL4 mechanisms
  ↓ property-specific evidence
Observed / machine-checked system claim

Potential tools and concepts include Isabelle/HOL, abstract and executable specifications, refinement, invariants, Hoare logic, l4v, trusted-computing-base analysis, semantic-policy-to-topology refinement, and temporal-contract-to-scheduler/configuration verification.
