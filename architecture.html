Architecture

A responsibility graph, not a numbered pipeline.

Semantic requirements describe what must hold. Sibling workload planes execute actions and streams. A separate control plane proposes, verifies and installs a machine realization that seL4 can enforce.

Transaction Server remains the historical/AN2 subsystem name. The canonical per-request abstraction is Invocation/Action unless explicit transaction semantics are declared.

Control plane: propose, verify, install

A single “Planner / Policy Compiler” box hid too much authority. The corrected model separates three responsibilities even if an MVP initially co-locates them:

Semantic contracts + resource state
              ↓
       Candidate Planner
              ↓
   Plan Verification / Admission
              ↓
 Privileged Reconciler / Installer
              ↓
      installed machine topology

The planner may search for a realization. The verifier/admission step checks authority non-amplification and semantic/resource/temporal requirements. Only the installer owns the privilege to mutate concrete capability/resource/scheduling topology.

Why the split matters: seL4 enforces the capabilities actually installed. If an unrestricted compromised planner can install arbitrary capabilities, the kernel cannot infer that those capabilities violate a higher-level semantic policy.

Some authority can be structural. Argument predicates, purpose/context constraints and similar semantics may still require trusted runtime guards. The architecture treats those guards as first-class plan obligations instead of pretending all policy disappears into kernel capabilities.

Real-time is a cross-cutting contract

Real-time is not a third sibling fabric. An invocation can be best-effort, soft-real-time or hard-real-time; a stream can also have timing constraints. The semantic contract names the requirement, while planning/admission derives scheduler/resource configuration and runtime enforcement.

TemporalContract
deadline · period/MIT · jitter · criticality · blocking constraints
               ↓
candidate resource / scheduling plan
               ↓
admission / schedulability assumptions
               ↓
installed priority · budget · period · CPU · reservations
               ↓
bounded runtime path + measured/proved evidence

Numeric scheduler priority is therefore an implementation-plan output, not semantic object truth.

Three different kinds of time

KindQuestionExamples
Stream / event timeWhen was an observation produced and how is late/out-of-order data handled?timestamps, windows, retention, replay
Causal / logical orderWhat depends on what?happened-before, derivation links
Execution / real-timeBy when must work complete under which assumptions?release, deadline, jitter, WCET, blocking, resource budgets

Distributed timing additionally requires a clock model: named clock domains, synchronization assumptions, uncertainty and explicit start/completion boundaries.

SystemPlan is a manifest, not a god-object

SystemPlan revision
  ├─ semantic contract revisions
  ├─ AuthorityPlan
  ├─ PlacementPlan
  ├─ ResourcePlan
  ├─ SchedulingPlan
  ├─ RecoveryPlan
  └─ ResidualGuardSet references

Consistency/conflict requirements belong to object/class contracts. Placement and replication choices belong to plans that demonstrate how those requirements are met. Recovery may change realization, but not semantic authority or consistency requirements silently.
