Open research

Uncertainty is part of the architecture.

The goal of this page is not to decorate unknowns with confident boxes. It makes the questions explicit enough that experiments, proofs, or repository evidence can close them.

Semantic authority and installation

  1. How should semantic authority compile into structural machine authority plus explicit residual guards?
  2. What independent checks must a CandidatePlan pass before privileged installation?
  3. Can the planner be constrained by a capability envelope, or must verifier and installer be stronger isolation boundaries?
  4. How should delegation, attenuation, revocation and authenticated SubjectContext binding interact with object lifecycle?

Invocations, streams, provenance

  1. Which explicit retry/idempotency/commit semantics should each effectful Invocation declare?
  2. How should streams handle event time, ordering, backpressure, sampling, retention and loss?
  3. How should provenance/causality be captured without conflating it with timestamps or contaminating deadline-critical paths?
  4. How should observed, derived/estimated, desired/configured and commanded state remain distinguishable under concurrent updates?

Temporal contracts and real-time

  1. What is the first local clock model, release point and completion boundary?
  2. Which temporal fields are semantic requirements and which scheduler parameters belong only to SchedulingPlan?
  3. How are WCET/interference assumptions obtained, represented, and validated?
  4. Which admission/schedulability method is appropriate for the first target?
  5. How should blocking, priority inversion and temporal isolation be bounded?
  6. Which topology/resource changes require re-admission?
  7. What synchronization/uncertainty model is needed before distributed timing claims?

Refinement and verification

  1. Can SemanticContracts → CandidatePlan → VerifiedPlan → InstalledPlan be refined or checked against concrete capability/resource topology?
  2. Can temporal contracts be related to scheduling/resource configuration with machine-checkable guarantees?
  3. Which bounded end-to-end property is small enough to verify first yet important enough to matter?
  4. Does the architecture demonstrate a measurable property beyond a strong conventional distributed stack, or should the “new OS class” claim be narrowed?
Research discipline: if an experiment does not show a material difference, narrow the claim instead of adding layers.
